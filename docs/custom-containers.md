# Creating and Selecting Custom NITA Images

NITA runs the Webapp and Jenkins as persistent Kubernetes workloads. Ansible
and Robot images are used for ephemeral workloads generated by Jenkins. Make
customizations in a Dockerfile and build a new image; do not edit a running
container and expect those changes to persist.

## Build a Custom Image

This example builds a custom Jenkins image from the checked-out component
repository. BuildKit supplies the target architecture to the Dockerfile, so no
host-architecture argument is needed:

```shell
cd /opt/nita-jenkins
docker build --tag registry.example/team/nita-jenkins:validation .
docker push registry.example/team/nita-jenkins:validation
```

To publish one tag for both supported platforms from a suitably configured
builder:

```shell
docker buildx build \
  --platform linux/amd64,linux/arm64 \
  --tag registry.example/team/nita-jenkins:validation \
  --push .
```

For an offline cluster, build for the cluster's platform, save the image, and
import it into containerd:

```shell
docker save registry.example/team/nita-jenkins:validation \
  --output nita-jenkins-validation.tar
sudo ctr --namespace k8s.io images import nita-jenkins-validation.tar
```

## Select Complete Image References

The installer and `k8s/apply-k8s.sh` accept complete image references. Set only
the component you want to replace; other components retain their canonical
`ghcr.io/juniper/...:latest` defaults:

```shell
export NITA_JENKINS_IMAGE=registry.example/team/nita-jenkins:validation
sudo -E ./install.sh
```

The available variables are:

| Variable | Workload |
|---|---|
| `NITA_WEBAPP_IMAGE` | Persistent Webapp deployment |
| `NITA_JENKINS_IMAGE` | Persistent Jenkins deployment |
| `NITA_ANSIBLE_IMAGE` | Jenkins-generated Ansible workloads and standalone pull |
| `NITA_ROBOT_IMAGE` | Jenkins-generated Robot workloads and standalone pull |
| `JUNOS_MCP_IMAGE` | Optional Junos MCP deployment |

Tags and immutable digests are both valid. Digest pinning is preferred when a
deployment must be exactly reproducible:

```shell
export NITA_WEBAPP_IMAGE=ghcr.io/juniper/nita-webapp@sha256:<digest>
export NITA_ANSIBLE_IMAGE=registry.example/team/nita-ansible:test
export NITA_ROBOT_IMAGE=registry.example/team/nita-robot:test
sudo -E ./install.sh
```

Jenkins receives the Ansible and Robot values as environment variables, so the
ephemeral pod manifests it generates use the same selected references.

## Apply an Override to an Existing Installation

Export the reference and re-render the NITA manifests:

```shell
cd /opt/nita/k8s
export NITA_JENKINS_IMAGE=registry.example/team/nita-jenkins:validation
sudo -E ./apply-k8s.sh
kubectl rollout status deployment/jenkins --namespace nita
```

If an image was imported directly rather than pushed to a registry, ensure its
reference exactly matches the override. Kubernetes uses the complete value
verbatim and does not append a registry or tag.

## Architecture Boundary

The component workflows produce GHCR manifests for `linux/amd64` and
`linux/arm64`. Existing canonical packages may remain amd64-only until the
publisher changes land and run on upstream `main`; inspect the selected
manifest before scheduling it on ARM. The upstream ARM stack test remains
gated until all four canonical component packages contain real ARM application
images. Full host installation on ARM Linux is still experimental;
`install.sh` continues to warn on non-x86_64 hosts.
